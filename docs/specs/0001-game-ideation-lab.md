# 0001 — Game Lab：AI 原生游戏立项实验室

- **状态**：Draft
- **负责人**：Product / PM
- **创建日期**：2026-10-02
- **关联原型**：`lab.html`
- **关联项目**：Game Analyzer

## 1. 问题

游戏立项阶段最常见的失败不是“没有想法”，而是：

1. 机制假设来自少数人的经验判断，缺少系统化证据；
2. 品类、玩法、动机和商业模式经常被混在一起讨论；
3. 立项前缺少低成本验证手段；
4. 大量玩法讨论停留在“感觉可行”，没有可量化信号；
5. 一次试玩结论无法沉淀为可复用的机制知识。

Game Lab 要解决的是：

> 把“几个人在会议室里侃侃而谈”的玩法组合，变成“有证据、有原型、有实验、有数据回流”的机制验证流程。

## 2. 用户

### 2.1 目标用户

- 游戏产品经理
- 游戏策划
- 立项评审委员会
- 独立开发者
- 小型孵化团队

### 2.2 用户任务

1. 输入多款竞品或品类样本；
2. 看清玩家动机、口碑缺口和未被满足需求；
3. 生成可测试的机制假设；
4. 得到最小可玩原型方案；
5. 设计对照实验并定义核心指标；
6. 回收试玩数据；
7. 判断机制是否值得进入下一轮；
8. 沉淀机制知识库。

## 3. 非目标

Game Lab **不追求**以下目标：

1. 一键生成完整商业游戏；
2. 自动替代策划创意；
3. 直接预测爆款；
4. 只做评论情感分析；
5. 只做 AI 代码生成；
6. 忽略人工评审与判断。

## 4. 核心概念

### 4.1 玩家动机

指玩家真正想要的心理满足，而不是品类标签。

示例：

- 收集
- 养成
- 建造
- 自动化
- 探索
- 掌握
- 协作
- 竞争
- 表达
- 经营
- 随机性
- 叙事代入

### 4.2 机制假设

不是“做一个类似某某的游戏”，而是一个可验证的条件命题：

> 对于哪类玩家，在什么场景下，哪个机制组合能产生哪种体验，并带来哪些行为信号。

### 4.3 最小可玩原型

用于验证单一机制假设的 5-15 分钟游戏切片，不是完整游戏。

### 4.4 实验验证

通过对照组、行为数据和主观反馈判断机制是否成立。

### 4.5 机制知识库

记录“机制 → 动机 → 效果 → 边界条件 → 失败原因”的结构化知识，而不是简单的游戏案例库。

## 5. 产品主线

```text
1. 输入竞品集合
2. 识别玩家动机
3. 找到口碑缺口
4. 生成机制假设
5. 生成最小可玩原型
6. 设计实验方案
7. 采集试玩数据
8. 输出机制判定
9. 生成下一版假设
10. 沉淀机制知识库
```

## 6. 功能需求

### 6.1 P0

1. **竞品输入**
   - 支持录入多款竞品；
   - 支持标注平台、品类、样本量、时间窗口；
   - 支持导入评论或口碑数据。

2. **动机分析**
   - 从评论中识别玩家动机；
   - 输出动机强度、频次和情绪倾向；
   - 区分“被满足”和“未被满足”的动机。

3. **口碑缺口**
   - 识别跨竞品重复出现的抱怨；
   - 识别只有单款产品出现但强度很高的问题；
   - 输出机会假设候选。

4. **机制假设卡**
   - 输出目标玩家、动机组合、机制组合、差异化点、先例和风险；
   - 每张卡片必须能回答“为什么要做”和“如何验证”。

5. **原型方案**
   - 输出 5-15 分钟可玩切片；
   - 明确核心循环、操作、目标、胜利条件和埋点；
   - 不追求美术完整性。

6. **实验设计**
   - 自动生成对照组和实验组；
   - 定义核心行为指标和主观指标；
   - 定义最低通过门槛。

7. **数据回流**
   - 采集进入、教学、核心循环、失败、重开、分享等事件；
   - 输出行为漏斗和卡点分析。

8. **机制判定**
   - 判断机制是否值得进入下一轮；
   - 输出证据链和失败原因；
   - 记录人工评审结论。

### 6.2 P1

1. 机制知识库；
2. 多轮实验版本对比；
3. 竞品动机雷达；
4. 原型模板系统；
5. 自动生成下一版机制假设。

### 6.3 P2

1. 大模型辅助生成；
2. 自动生成代码级原型；
3. 自动招募试玩用户；
4. 多平台数据采集；
5. 立项报告导出。

## 8. 交互设计

### 8.1 页面结构

1. **输入**
   - 竞品集合
   - 玩家动机
   - 口碑缺口

2. **假设**
   - 机制假设卡
   - 差异点
   - 先例
   - 风险

3. **原型**
   - 核心循环
   - 操作说明
   - 埋点
   - 时长

4. **实验**
   - 对照组 / 实验组
   - 指标
   - 通过门槛

5. **结果**
   - 行为漏斗
   - 主观反馈
   - 机制判定

6. **迭代**
   - 下一版方向
   - 保留项
   - 修改项
   - 放弃项

7. **知识库**
   - 机制
   - 动机
   - 效果
   - 边界条件

### 8.2 关键原则

- 结论必须可解释；
- 每个假设必须可验证；
- 每个实验必须有对照组；
- 每个结果必须能回流；
- 人始终掌握最终判断权。

## 9. 成功标准

### 9.1 产品级成功标准

1. 用户能在 10 分钟内理解完整流程；
2. 用户能从机制假设卡看出“为什么要做”和“如何验证”；
3. 至少一个机制假设进入真实试玩；
4. 至少一个机制判定被团队采纳或明确否决；
5. 机制知识库开始积累有效与失败案例。

### 9.2 实验级成功标准

单个机制假设至少满足：

- 50% 玩家完成 10 分钟流程；
- 30% 玩家愿意重玩；
- 20% 玩家认为机制有潜力；
- 对照组与实验组在核心指标上出现可解释差异。

## 10. 边界与风险

### 10.1 风险

1. 数据源不完整；
2. 动机识别过粗；
3. 机制假设过度依赖先例；
4. 原型生成质量不稳定；
5. 行为数据样本量不足；
6. 用户把“实验信号”误读为“爆款预测”。

### 10.2 缓解策略

1. 所有结论附证据链；
2. 每个机制假设必须写明适用边界；
3. 保留人工评审环节；
4. 最小原型只验证一个假设；
5. 报告中明确“实验结论”和“商业判断”的区别。
